# Alaya: design decisions

A record of what we have decided, in order. Each line is final until we change it on purpose.

| # | Question | Decision | Date |
| --- | --- | --- | --- |
| 1 | What kind of OS | Our own kernel, from scratch, booting in QEMU first, maybe a real PC later | 2026-11-19 |
| 2 | Not in scope | No website, no microcontroller, no personal content. Nothing carries over from the old spec | 2026-11-19 |
| 3 | CPU | x86-64 | 2026-11-19 |
| 4 | Language | Rust | 2026-11-19 |
| 5 | Kernel structure | Microkernel: memory, scheduling and messages in the kernel; drivers and files as separate programs | 2026-11-19 |
| 6 | Boot | Limine bootloader | 2026-11-19 |
| 7 | Security | Capabilities: a program can only use what it holds a handle to | 2026-11-19 |
| 8 | Messages | Synchronous calls with replies, plus short asynchronous notifications (seL4 style) | 2026-11-19 |
| 9 | Memory | User space decides: the kernel allocates nothing and builds its objects from raw memory capabilities that programs give it (seL4 style) | 2026-11-19 |
| 10 | Cores | Revised: designed for many cores from day one (one big kernel lock, a run queue per core, thread-safe servers); the first milestone may run on one core | 2026-11-19 |
| 11 | Scheduler | Revised: fixed priorities plus time budgets (scheduling contexts, seL4 MCS style); servers run on their caller's budget | 2026-11-19 |
| 12 | Program interface | Our own capability-based API first; the POSIX layer follows (made firm by 21, built per 31) | 2026-11-19 |
| 13 | First interface | A graphical desktop (windows and a mouse) is the goal from the start. Kernel debug output still goes to the serial port | 2026-11-19 |
| 14 | Windows | A compositor program owns the screen; each app draws its own pixels into a buffer it shares with the compositor (like Wayland) | 2026-11-19 |
| 15 | Disk format | Our own filesystem, designed for this OS | 2026-11-19 |
| 16 | Crash safety | Copy-on-write: never overwrite in place; write new blocks, then switch one root pointer. Snapshots come almost free | 2026-11-19 |
| 17 | File view | Revised by 22: one tree for the person and the trusted desktop; apps see only their own folder and their grants | 2026-11-19 |
| 18 | Open check | Revised by 22: grants, capabilities that carry what, rights and when (live, pinned, until), issued by open/save dialogs, drag and drop, and install-time requests | 2026-11-19 |
| 19 | First drivers | Revised: virtio (QEMU) first, then one real reference PC (NVMe, USB, HD Audio, network, one GPU family); each driver is its own restartable program | 2026-11-19 |
| 20 | License | Revised: GPL-3.0 for kernel, servers and drivers, plus a linking exception for the system libraries apps link against | 2026-11-19 |
| 21 | Games | Native games, Linux/Vulkan games ported through SDL, and later Windows games through a Wine/Proton-style layer. This makes the POSIX layer (decision 12) a firm requirement, sized for what Wine needs | 2026-11-19 |
| 22 | Signature feature | History and grants (`concept-history-and-grants.md`) with the storage classes from `battle-test.md`: every commit attributed to a capability, history by retention rule, per-app undo, branches, opt-in replay | 2026-11-19 |
| 23 | Reference PC | A laptop with an NVIDIA RTX 4050 and an Intel Core i7 13th gen (hybrid graphics: the Intel Iris Xe built-in GPU drives the screen, the NVIDIA GPU renders; the CPU mixes performance and efficiency cores). GPU path: a kernel-side driver using NVIDIA's GSP firmware, plus Mesa's NVK Vulkan driver (MIT) in user space | 2026-11-19 |
| 24 | Out of memory | Compress idle memory in RAM first, then ask apps to free caches, then stop the lowest-priority app. No disk swap. The foreground game and the compositor are never stopped. Each app has a memory budget | 2026-11-19 |
| 25 | Network | Open by default: every app can reach the network, as on Windows and Linux. Note: an app that was granted files can send them anywhere | 2026-11-19 |
| 26 | Kernel interface | Accepted as drafted in `kernel-interface.md`: 10 calls, everything else is a call on a capability; close to seL4 with MCS, plus huge pages, IOMMU domains and core types | 2026-11-19 |
| 27 | Leak guard | Network stays open, the ledger records every connection, and any app can be cut off. Once an app reads a file marked private, it needs the person's OK before going online. The mark spreads: an app that receives data or shared memory from a marked app is marked too | 2026-11-19 |
| 28 | Updates | Each system update installs on a branch of the store and the machine boots from it. Limine keeps an entry for the current and the previous system, and a boot counter falls back automatically if the new one fails to boot or the person rejects it | 2026-11-19 |
| 29 | Disk encryption | The whole store is encrypted (AES, using the CPU's AES instructions). The TPM releases the key after a short PIN at boot; a recovery key is shown once at setup for when the TPM or board is replaced | 2026-11-19 |
| 30 | People | Separate people: each has their own store branch of files, history, grants and encryption key (unlocked at login with their own PIN or passphrase, on top of decision 29). Apps and games are installed once and shared, read-only | 2026-11-19 |
| 31 | POSIX layer | Port musl (MIT); its Linux calls are translated to our servers. Sized for Wine: threads, futex-style waits, mmap at fixed addresses, signals (incl. crash handlers), dlopen, posix_spawn, Unix sockets that pass open handles | 2026-11-19 |
| 32 | Testing | Accepted as drafted in `test-plan.md`: TLA+ and Kani proofs of revocation, scheduler and commits; fuzzing; power-cut and driver-crash injection; hard gates on the reference laptop under full load | 2026-11-19 |
| 33 | History size | Only changed blocks are stored. Storage classes per battle test (documents full history, apps and games current plus one pre-update snapshot, caches none). Thinning: every moment for a day, hourly for a week, daily for a month, weekly after. History budget: 15 % of the disk by default, oldest pruned first. The timeline only shows this history and costs no extra space | 2026-11-19 |
| 34 | Desktop | Familiar floating windows plus a timeline to see files and the desktop as they were, and a grants badge on each window. Implementation requirements in `timeline.md`, including per-file keys so "forget" erases a file from all history | 2026-11-19 |
| 35 | Name | Alaya (ah-LAH-yah): the storehouse of memory that keeps every past impression. A full trademark check is still needed before public use | 2026-11-19 |
| 36 | Backup | Each person's store and its history stream, encrypted end to end, to an external drive or another Alaya machine, and optionally to cloud storage the person chooses (any S3-compatible or WebDAV service; Alaya runs no service of its own). Incremental by commit. Keys never leave the machine, so restoring needs the recovery key. "Forget" also makes the file unreadable in every backup, because its key is gone. Runs on a background budget and pauses on battery or metered networks | 2026-11-19 |
| 37 | Apps | Signed bundles from any source, no gatekeeper. A bundle's manifest lists the grants it asks for at install (folders, camera, microphone, game controllers). Updates must be signed by the same developer key. Installs and updates happen on a branch the person approves; apps are installed once, read-only, shared by all people. A per-person developer mode allows unsigned builds, with a clear warning | 2026-11-19 |
| 38 | Clipboard | Classic (confirmed: desktop-only judged safe but not useful): any app can read the clipboard at any time. To keep decision 27 whole, clipboard content copied from a marked (private) app carries the mark, and an app that reads it is marked too; every clipboard read is recorded in the ledger | 2026-11-19 |
| 39 | Search | The desktop indexes each person's files and their history; picking a result hands that file to an app as a grant, and saved searches can be granted like folders. The index is encrypted with the person's key, built on a background budget, never shows private files to anyone but their owner, and "forget" removes a file from it | 2026-11-19 |
| 40 | Terminal | Full access: commands run in the terminal see the person's whole tree, like Linux. Limits that still hold: only that person's own files (never another person's); every change is attributed and undoable through history; reading private files still triggers the leak guard. Risk accepted: a script run in the terminal can touch any of the person's files | 2026-11-19 |
| 41 | SDK | Written in Rust, the primary path for apps, with a stable versioned C interface so C, C++ (game engines), Zig, Go and others can use it | 2026-11-19 |
| 42 | Accessibility and languages | Built in from the start: the UI toolkit carries an accessibility tree (screen reader, full keyboard use, scaling, high contrast) and all text is UTF-8 and translatable, including right-to-left scripts, from the first desktop (milestone 6) | 2026-11-19 |
| 43 | Recovery | Both: a small read-only recovery system on the disk (opened by a key at boot or after 3 failed boots) that can roll back to any past system, repair the store, restore from backup or reset; plus an optional recovery USB stick for a dead disk. Recovery needs the PIN or the recovery key to touch data; reset erases by destroying the keys | 2026-11-19 |
| 44 | Crash reports | Every crash is saved locally as a readable report; nothing is sent unless the person reviews it and chooses to. Reports never include file contents or names of private files. App crashes go to the address the app's manifest names; system crashes to the Alaya project. A kernel crash is saved to a reserved area and shown at the next boot | 2026-11-19 |
| 45 | Power and heat | Automatic: full speed plugged in, balanced on battery. A thermal governor reads the CPU and GPU temperatures and lowers time budgets and clocks smoothly before the hardware's own throttling starts, so frame times stay steady rather than spiking. Per-game overrides (for example a frame cap on battery) | 2026-11-19 |
| 46 | Background apps | An app with no visible window is frozen (no CPU) unless it holds a background grant (music, downloads, chat). Notifications need a grant too, go through the desktop, and are silenced during full-screen games | 2026-11-19 |
| 47 | Clocks (proposed, not objected to) | History is ordered by a commit counter that only goes up, never by the wall clock, so a wrong or changed clock cannot scramble the timeline; wall-clock times are only labels. Time is set from the hardware clock and kept by authenticated network time (NTS) | 2026-11-19 |
| 48 | Displays | Full modern displays from the first versions: several monitors with hotplug, per-monitor scaling (fractional, mixed DPI), high refresh rates, variable refresh rate, HDR with colour management, and the laptop's built-in panel plus external screens on the reference laptop | 2026-11-19 |
| 49 | Peripherals | Bluetooth first (wireless game controllers, headsets with low-latency audio, mice and keyboards), as its own restartable driver and server; pairing a device is a desktop action, and an app reaches a device only through a grant. Printing and scanning come later, driverless only (IPP Everywhere / eSCL), so no vendor drivers are needed | 2026-11-19 |
| 50 | Input methods | A built-in input-method server sits between the keyboard and apps: keyboard layouts, dead keys, composing scripts (Chinese, Japanese, Korean and others), emoji and on-screen keyboard, in every app from the first desktop. Only the focused window receives keys; apps never read the keyboard directly | 2026-11-19 |
| 51 | Object lifetime | Dropping the last handle to a kernel object frees nothing; its memory comes back only when the untyped it was made from is revoked (no seL4 zombies). Each program has one flat handle table. A revoke in progress always deletes faster than other cores can copy, so it always finishes | 2026-11-19 |
| 52 | Linux compatibility (for Claude Code) | Two parts. Now: Claude Code runs on the host PC and drives Alaya in QEMU (build, serial log, GDB stub, QEMU control socket). Inside Alaya: grow the POSIX layer (31) until Node.js, bash, git, ripgrep and basic command-line tools are recompiled for Alaya, and run Claude Code's JavaScript bundle on that Node. The POSIX layer gains `fork` (needed by bash), Linux-style `epoll`, `eventfd`, `timerfd` and `inotify` (so ports need few patches), pseudo-terminals, and the right to make writable-then-executable memory for JIT engines. Lands in milestone 8b, before the first boot on real hardware; USB networking comes in milestone 11 so it reaches the internet before Wi-Fi exists (user chose this over a Linux system-call personality and a Linux VM). `fork` approved with the child holding exactly the parent's grants. Rules in `linux-compat.md` section 7; where Alaya's versions go beyond Linux (process families in the ledger, file watching from the commit stream, sessions on a branch) in section 8 | 2026-11-19 |
| 53 | Time budgets refill | Sporadic refills, as in seL4 MCS: time used in one stretch starting at s comes back one period after s, so a thread never runs more than its budget in any window of one period (user confirmed my recommendation) | 2026-11-19 |
| 54 | Core placement | The kernel places threads: a scheduling context names a core type (any, performance, efficiency) and optionally one core; when a thread wakes the kernel picks an idle core of that type, else the one running the least important work; idle cores pull waiting work. Running threads are never moved (user chose this over pinned scheduling contexts with a user-space placement service) | 2026-11-19 |
| 55 | Budget runs out in a server | A server running on its caller's budget that runs out waits for the caller's next refill; the slow caller pays for itself. Timeout messages to a handler can be added later (milestone 4) without changing this | 2026-11-19 |
| 56 | Address spaces | Arrive in milestone 3. Each address space is given an untyped of its own, and the kernel takes page tables from it as mappings need them, so the kernel still allocates nothing and programs only map pages | 2026-11-19 |
| 57 | Principles | Eight principles with always / never / how we check (`principles.md`), designed in depth in `principles-design.md`. When they clash: safe data, then steady performance, then games, then privacy. Network stays open by default (25 confirmed). Deep anti-cheat moves from never to not yet | 2026-11-19 |
| 58 | Saving | Alaya apps keep work automatically; Save becomes 'name this version'. Named versions are never thinned out (warn when history space is full). Older apps keep their own Save | 2026-11-19 |
| 59 | Admin | Classic admin like Linux: needs PIN each time; admin changes are kept in history and undoable; admin cannot read another person's files (per-person keys) | 2026-11-19 |
| 60 | Install list and screen capture | Any item an app asks for at install can be unticked and changed later. Screen capture is allowed once per app, with a red light and the app's name whenever it captures | 2026-11-19 |
| 61 | Crashes and updates | A crashed app reopens where you were (a second crash within a minute shows a message). Updates prepare in the background on a branch and apply at next restart; never forced | 2026-11-19 |
| 62 | Forget | Confirm, file hidden at once, key destroyed after one hour; can be cancelled until then | 2026-11-19 |
| 63 | Games | Full-screen games pause backups, indexing and update preparation (background-grant apps keep running). Frames capped to refresh rate by default, uncap per game. Steam's Windows version through the translation layer is the main target. Mods live in a personal layer per game per person | 2026-11-19 |
| 64 | Claude Code | Each session asks at the start: side branch or directly. Private files are invisible to Claude Code unless handed over one at a time, logged as sent online | 2026-11-19 |
| 65 | Updates and contributions | Updates are signed plain files on the public repository's releases, mirrorable; the computer sends nothing about you. Outside code contributions closed until the core is stable | 2026-11-19 |
| 66 | Claude Code inside Alaya (replaces the Claude Code part of 52) | Claude Code now ships only as a native Linux program (no Node.js), so running its JavaScript on a ported Node no longer works. Inside Alaya, a "Linux world" runs it unchanged: a user-space Linux server answers Linux system calls (the kernel turns them into fault messages to it, like Starnix and the first WSL); its file changes go through the store (attributed, undoable, sessions on a branch), its connections through the ledger and leak guard, JIT memory is a right it must hold. Claude Code on the host driving QEMU stays. The bash, git and ripgrep ports for the terminal stay (user chose this over host-only and a Linux VM). Analysis: `concept-analysis.md` | 2026-11-19 |
| 67 | Show the new idea early (changes the timing in 42, 48 and 50) | Milestone 6 becomes a simple desktop (one monitor, basic keyboard, the toolkit built with its accessibility tree and UTF-8 but only basics on), so history and grants (7) arrive sooner. A new milestone 7b brings multiple monitors with hotplug and fractional scaling, the input-method server, the screen reader, high contrast and right-to-left text; HDR comes with accelerated graphics (9). The decisions themselves stand; only when they land changes (user chose this over keeping the full first desktop) | 2026-11-19 |
| 68 | New ideas: "What happened?" and re-run | Two ideas from `new-ideas.md` join the design. **What happened?**: the desktop turns the ledger into plain sentences ("the photo editor changed 12 photos at 14:02"), per person, with an undo button on each line; private files are shown only to their owner. **Run it again**: open an app with exactly the files it read at a past moment (pinned, read-only grants built from the ledger's record of reads), to compare with today. Both land in milestone 7. The outbox and the AI helper contract wait for later (user chose this over adding all four) | 2026-11-19 |
| 69 | Everyday ideas: tasks, one undo, file stories | Three ideas from `new-ideas.md` Part B join the design. **Tasks, not apps**: the desktop is organised by tasks; a task holds its windows, files, web pages, notes and its own timeline; switching task swaps the desktop; a paused task uses no CPU or memory and resumes exactly (Alaya apps restore their state, older apps are reopened); an app opened in a task is granted that task's files without a question, and nothing else (the terminal keeps decision 40's rule). **One undo for the whole computer**: one key walks back the person's own recent actions across everything (file moves, renames, deletes, settings, installs, closed windows), newest first, with a visible list. **File stories**: each file shows where it came from and what was made from it, read from the ledger. All three land in milestone 7, the desktop parts with milestone 6's simple desktop where possible (user chose this over tasks only, undo and stories only, or all seven) | 2026-11-19 |
| 70 | Lower-level ideas: deadlines, no-restart updates, quiet driver crashes | Three ideas from `new-ideas.md` Part C join the design. **Frame deadlines**: the display's next refresh becomes a deadline carried with messages and GPU fences through every program in the chain (input, game, GPU driver, compositor), on the game's time budget, and Alaya records which link missed; kernel support in milestone 4, compositor in 6, GPU in 9. **Updates without restart**: drivers and system servers are updated live by starting the new version and handing it the old one's state (milestone 4 for drivers, servers as they arrive); the kernel itself later (after milestone 12); until then decision 61 still applies to kernel updates only. **Quiet driver crashes**: a small helper outside each driver keeps its unfinished requests and sends them again after a restart, so apps see no error (milestone 4) (user chose this over adding never-turning-off too, deadlines only, or none) | 2026-11-19 |
| 71 | Terminal and Claude Code in tasks (changes 40) | A terminal, the Linux world and Claude Code opened in a task see only that task's files; one click opens them to all of the person's files, recorded in the ledger. Outside tasks, decision 40 is unchanged. Never another person's files; the private-file guard still applies (user confirmed my recommendation, contradiction A1) | 2026-11-19 |
| 72 | The everywhere area (with 69 and 46) | Apps not tied to one task (music, chat, downloads) live in an "everywhere" area and keep running whatever task is active, if they hold a background grant (46). They see only their own folder and what the person hands them, never a task's files automatically (user confirmed my recommendation, contradiction A2) | 2026-11-19 |
| 73 | When live updates apply (changes 61) | Updates that need no restart (70) apply by themselves when no full-screen game is running, still on a branch (28), with a short note and one-click undo. Updates that still need a restart (the kernel, until it can be swapped live) keep decision 61: prepared quietly, applied at the next restart, never forced (user confirmed my recommendation, contradiction A3) | 2026-11-20 |
| 74 | Admin and the login screen (with 59) | If the login screen or the key-handling parts of the system changed since a person's last login, Alaya tells that person before they type their PIN. The check is measured at boot and tied to the TPM (decision 29), so an admin cannot hide it. Admin changes otherwise stay as in 59 (user confirmed my recommendation, contradiction A4) | 2026-11-20 |
| 75 | Testing real hardware | Linux stays in charge of the reference laptop. Real devices (USB controller, Wi-Fi card, sound, the NVIDIA card) are handed one at a time to Alaya running in KVM to test its drivers. A ready-to-boot check (all stress gates, proofs and a 72-hour soak) comes first; the first real boot, from a USB stick that never touches the laptop's disk, happens only after it passes and the person agrees. The Intel display driver, touchpad, battery, sleep and thermal control are finished at that first boot (user confirmed my recommendation, contradiction A5) | 2026-11-20 |
| 76 | How Alaya starts on real computers (changes 6 and 28) | Limine stays for development, the virtual machine and older PCs. Before the ready-to-boot check (milestone 13), Alaya gets its own small UEFI start-up program in Rust that reads the store, counts failed starts and falls back to the previous system by itself (28), records every step in the TPM so the disk key (29) and the login-change warning (74) can be trusted, and then starts the kernel (user confirmed my recommendation; `foundations-review.md`) | 2026-11-20 |
| 77 | Foundation additions (proposed, not objected to) | At the start of milestone 4: the processor's safety switches (SMEP, SMAP, UMIP), tagged memory maps (PCID), a format version on every kernel object plus one list of all kernel-wide state (for live kernel swap, 70), and protections against speculative-execution leaks (Spectre family). The QEMU runner enables an Intel IOMMU. The big kernel lock is measured under many-program load in milestone 4 (`foundations-review.md`) | 2026-11-20 |
| 78 | A driver that keeps crashing (milestone 4) | Up to 3 quick restarts in a minute; after that the device is switched off, waiting requests get a clear error, and the person sees a note with a try-again button (user confirmed my recommendation) | 2026-11-20 |
| 79 | Unfinished jobs after a driver crash (milestone 4) | The keeper sends every unfinished request again after a restart; drivers are written so doing a request twice changes nothing (same data written again, duplicates ignored), so apps never see an error (user confirmed my recommendation) | 2026-11-20 |
| 80 | Live update trial (milestone 4) | After a live update the keeper keeps the old version and its state for 10 minutes; if the new version crashes in that time, the old version comes back with that state and the person sees a short note (user confirmed my recommendation) | 2026-11-20 |
| 81 | Deadlines and importance (milestone 4) | Among threads of equal priority, the one whose deadline is sooner runs first (earliest deadline first within a priority level); priority always wins over deadlines, so a game can never push aside more important system parts (user confirmed my recommendation) | 2026-11-20 |
| 82 | How loudly "needs a look" is shown (living validity, `commitments.md`) | Quietly: a mark on the file and a line in "What happened?"; a notification only for results the person marked "tell me" (user confirmed my recommendation) | 2026-11-20 |
| 83 | Living validity for older apps | Linux and Windows apps get marks too, from Alaya watching what they read, always labelled as Alaya's guess, never shown as certain (user confirmed my recommendation) | 2026-11-20 |
| 84 | AI helpers on the internet (narrows 25 for AI helpers only) | By default an AI helper reaches only its own AI service; any other place needs the person's OK the first time it is used, and each one is logged in the ledger. Other apps keep decision 25 (user confirmed my recommendation) | 2026-11-20 |
| 85 | Loose groups and protected tasks (changes 69) | Grouping is optional and light: a loose group is only a label, a file can be in many, suggestions are allowed, and it never changes what an app can see. Only a protected task the person confirms (after seeing its file list) limits its apps to its files, as in 69. The desktop works normally without groups or tasks (user confirmed my recommendation, `continuity.md`) | 2026-11-20 |
| 86 | Testing the desktop ideas | A clickable mock-up in the browser comes first (three scripted days: loose groups, protected tasks, resume with "since you left", the decision inbox, Finish, living-validity marks), then the real thing in Alaya (milestones 6 and 7a). No throwaway Linux prototype (user confirmed my recommendation, `continuity.md`) | 2026-11-20 |
| 87 | Windows can be tiled (adds to 34) | Windows stay the base of the desktop. Every window floats by default and can also be tiled: drag it to a screen edge to snap it to a half (top edge fills the screen), or switch a group, task or screen to tiling so its windows share the screen side by side without overlapping, all by mouse or keyboard. Each group and task remembers its own layout (user's request) | 2026-11-20 |
| 88 | When an app update wants more (answers-and-contracts.md) | The update installs at once with the old limits, so security fixes never wait; the person is asked about each new thing only when the app first tries to use it. An update never widens an app's promise by itself (user confirmed my recommendation) | 2026-11-20 |
| 89 | A shared home for your data (personal state plane) | Parked until Alaya runs everyday apps (around milestone 16); then a small opt-in version with one or two data types and two separately written apps. Handing work to another computer (portable authority) is parked too (user confirmed my recommendation) | 2026-11-20 |
| 90 | Looks: what you use Alaya for (`why-switch.md`) | At first setup each person picks one or more looks (Play, Everyday, Create, Build, or "show me everything"), changeable any time in Settings with nothing lost. A look only decides what is on screen; history, one undo, privacy rules, quiet driver crashes, self-undoing updates and smooth frames work the same in every look. Hidden features appear once, at the moment they help (for example "Alaya kept it. Undo?"). Simple version in milestone 6, full in 7a; the mock-up shows it first (user chose this over a single pick or no question) | 2026-11-20 |
| 91 | Gaming extras (`why-switch.md`, changes 33 for game saves) | **Why did it stutter?**: after a session with hiccups, one plain sentence names when and which part was late, from the deadline records of decision 70 (milestone 9). **Saves keep a history**: game saves are stored like documents, with full history, for every game (milestone 8). **Go back one version**: one click returns a game to its version before the last update (the copy decision 33 already keeps), and mods have "all off" and "back to clean" (decision 63) (milestone 14). Shown in the Play look (user chose all three) | 2026-11-20 |
| 92 | The Linux world runs everyday apps too (widens 66) | The Linux world is the main way to run everyday programs, not only Claude Code and developer tools: browsers, chat, editors, office apps and Steam's Linux version with Proton for Windows games. Each still gets Alaya's history, undo, grants, privacy guard and quiet crashes underneath. It must therefore be fast and complete enough for graphics, sound and games, not just the terminal. Alaya's own apps focus on what only Alaya can do. Milestone 14 runs Windows games this way (user chose this over keeping it for developer tools only) | 2026-11-20 |
| 93 | Other processors (`any-device.md`, changes 3 to "x86-64 first") | Groundwork now: all x86 details in the kernel move behind one wall, and the engine (the tests of milestones 0 to 4) also starts and passes on ARM in QEMU, kept passing in every later milestone (about 10 to 15% extra work each). One Alaya image carries a build per processor and the computer picks its own. Full ARM devices come in a new milestone after the first real boot. ARM tests also run where the chip really reorders memory (GitHub ARM machines, the Android phone via Termux), QEMU only. Microcontrollers like Arduino cannot run Alaya (user chose this over ARM alongside every milestone or PCs only) | 2026-11-20 |
| 94 | First ARM device: one open phone (`any-device.md`) | Milestone 17 aims at one phone model whose hardware is well documented by the open-source phone community (candidates such as the PinePhone Pro, Librem 5 or a phone with strong mainline Linux support; the exact model is chosen at the start of 17). It gets its own install image, since phones cannot start from a stick. Touch layout, battery, modem-free first (calls and mobile data later). Tested in QEMU first; the real phone only when Alaya is stable and the person agrees. Raspberry Pi and other ARM devices can follow (user chose this over the Raspberry Pi or an ARM laptop) | 2026-11-20 |
| 95 | Device sense: Alaya adapts to the kind of device (`any-device.md`) | Alaya guesses the form (desktop, laptop, convertible, tablet, handheld, phone, board, virtual machine) from what the device reports (firmware box type, battery, lid, touch, screen size, tilt sensor, board description, virtual-machine flag) and keeps its reasons. At first setup it shows the guess once ("This looks like a laptop") with a "that's not right" button, and suggests a look (decision 90) from it. After that it adapts by itself (docked, folded, unplugged), with a one-line note the first time each change happens. The form changes defaults only, never grants, history or protections; apps see only the form and input kinds, never serial numbers. Where a device lacks safety hardware, Alaya says so plainly. Basic in milestone 6, battery, lid and docking in 11 and 15, touch layout in 7b, handheld layout in 14 (user confirmed my recommendation) | 2026-11-20 |
| 96 | A tiny separate system for microcontrollers | Parked (a side project, not part of Alaya) | 2026-11-20 |
| 97 | Milestone 4b in two steps | First the processor wall alone (no change you can see on a PC, its own pull request), then the ARM build in QEMU as a second step | 2026-11-20 |
